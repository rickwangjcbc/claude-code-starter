# 導入・運用手順

## 1. 適用範囲
本雛形はClaude Code専用です。他製品のSkill配置や自動同期は含みません。
既存プロジェクトへ取り込む担当者・開発エージェント向けの手順です。ユーザー本人のターミナル操作を前提とする必要はありません。

## 2. 既存案件への取込み
- 新しい作業ブランチで、未コミット差分と既存のCLAUDE.md、settings、Skills、CIを確認する。
- 同名がある場合は全文を置き換えず差分をレビューして統合する。settings.local.jsonや認証情報を共有しない。
- 既存ルールと矛盾を解消し、案件の採用版と標準管理者を記録する。
- .gitignoreは既存の内容へ追記・統合する。既にGit追跡された秘密ファイルはignoreだけでは除外されない。
- team-のSkill名が既に使われていれば重複解消し、参照する依頼文も修正する。

## 3. 案件情報と検査の設定
`prompts/00-bootstrap.md`を使い、コードで判明する事項を調査する。
実行可能な検査をproject-checks.jsonへ登録する。次は構文例であり、Node案件の採用を要求するものではない。
```json
{
  "commands": [
    {"name": "unit", "argv": ["npm", "test", "--", "--run"], "timeout_seconds": 300},
    {"name": "lint", "argv": ["npm", "run", "lint"], "timeout_seconds": 120}
  ]
}
```
- 実際に定義されたコマンドへ置き換える。ローカルとCIの両方で必要な依存をlockから導入する。
- シェルの文字列連結は使わず引数配列を使う。`&&`やリダイレクトが必要ならレビュー済みスクリプトへ分離する。
- Windowsではnpm.cmd等の実行名が必要な場合がある。対象OSで起動を確認する。
- コマンド設定自体がコード実行の許可対象。外部由来の設定を未審査で実行しない。
- この実行器はSandboxではない。タイムアウトでもコマンドが生成した子孫プロセスまで完全停止する保証はない。サーバー常駐処理は登録せず、CIのジョブ制限と隔離を併用する。
- テストが存在しない案件では、受入条件に対応する最小テストを追加する計画を確認する。`true`、echo、雛形の自己試験だけをアプリ検証に登録しない。

## 4. Claude Codeでの実読込・権限確認
- 採用版、起動ディレクトリ、上位の組織設定や個人設定を確認する。
- `/context`（対応版では`/context all`）等でCLAUDE.md・Rulesの読込を確認する。
- `/`の一覧でteam-のSkillsを確認し、`/team-plan`を無害な練習タスクで明示起動する。
- `/permissions`で設定の反映を確認する。仮の秘密ファイルを隔離fixtureに作り、Read拒否を確認する。実秘密は読まない。
- Bash・Edit・Writeについて一回承認を確認する。上位の管理設定やモードによる差は記録する。
- denyのReadルールはBashやMCP経由の全アクセスを防ぐものではない。秘密値を置かない環境、Sandbox、OS権限、ネットワーク制限を併用する。
- 本配布ではHooks・MCP・Plugin・自動許可・配備処理を有効化しない。

## 5. GitHubのCIと統合制御
- 既存CIがある場合はai-standard.ymlをそのまま二重導入せず統合する。
- application-checksへ案件のランタイム設定、lockに基づく依存導入を追加する。
- Actionsは組織が承認した版を採用し、厳格運用ではレビュー済みcommit SHAへ固定する。本雛形のvタグは不変参照ではない。
- 必須チェックにtemplate-checksとapplication-checksを指定し、人のレビューを必須化する。管理者等のbypass権限も確認する。
- ブランチ保護やCODEOWNERSはこのZIPだけでは設定されない。人の承認者を確認してリポジトリ側で適用する。
- 隔離した試験PRで検査を故意に失敗させ、mergeが止まることを確認する。未設定アプリ検査の失敗を例外化して通さない。
- GitHubを使わない案件では同等の検査・承認を利用中の基盤へ設定する。

## 6. 日々の運用
- 要件が曖昧ならteam-plan、受入条件が明確ならteam-implement、障害ならteam-fix-bugを使う。
- 高影響変更のみ人の方針確認を挟み、軽微な変更は既存規約で進める。
- レビューは可能なら別セッションからteam-reviewで行い、仕様と差分を渡す。
- タスクごとにブランチ・worktreeを分ける。worktreeはセキュリティ隔離ではない。
- 会話が長くなったらteam-handoffで証跡を残す。個人メモリを唯一の共通知識にしない。

## 7. 標準の変更・復旧
- 共通資産の変更は理由・適用範囲・評価結果を添えてPRレビューする。
- 組織標準へ還流する前に案件固有情報と機微情報を除く。
- 案件への新版適用は承認して行い、無条件に最新版へ同期しない。
- 問題があれば標準を導入したcommitを確認し、他者の変更を壊さないrevert案をレビューする。reset --hardで戻さない。

## 8. 導入判定（未確認があればBLOCKED）
- [ ] PROJECT.mdの重要な未設定が解消し、人の承認者が確認されている
- [ ] 雛形構成検査と自己試験が成功している
- [ ] 案件の実検証コマンドがローカルとCIで成功している
- [ ] 対象版でCLAUDE.md、Skills、権限設定の実読込を確認した
- [ ] 秘密情報・ネットワーク・OS権限・Sandboxの境界を確認した
- [ ] 受入条件に対応した実動作を確認した
- [ ] 利用する基盤の人の承認・統合制御が機能することを確認した
- [ ] 未検証範囲・残存リスクを人の承認者が把握している

このチェックリストは導入判定の記録であり、自動の承認エンジンではない。雛形の検査成功だけで項目を自動的にチェックしない。
